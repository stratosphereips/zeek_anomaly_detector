Zeek Anomaly Detector Explained

This page documents the full design of the tool: what data it reads, how it builds features, how it correlates Zeek logs through uid and fuid, which anomaly-detection techniques it applies to each log type, how the directory score is constructed, how the normal baseline works, and why those design choices were made.

Inputs: Zeek TSV and Zeek JSON
Modes: single log or whole directory
Core idea: one detector does not fit every Zeek log
Outputs: anomalies, directory score, JSON, PDF, summary line

Purpose

The tool is built to analyze Zeek logs as an investigation set, not just as isolated files. Its goal is to rank suspicious flows, transactions, files, events, and operational states, then summarize the whole directory as a directory-level maliciousness score.

What it is not

It is not a single global unsupervised model applied blindly to every Zeek schema. Zeek logs describe very different things: flows, web transactions, files, inventories, alerts, telemetry, and runtime state.

What it is

It is a multi-stage analysis pipeline with log-specific feature builders, log-specific scorers, cross-log context, and a final directory-level aggregation step.

Input Data

The detector accepts either one Zeek log file or a whole directory of Zeek logs. It auto-detects the on-disk format.

Supported file formats

  • Classic Zeek TSV logs with #fields headers
  • Line-delimited Zeek JSON logs

Common log types

  • conn.log, http.log, dns.log, files.log
  • ssh.log, tls.log, ssl.log
  • weird.log, notice.log, stats.log
  • known_hosts.log, known_services.log, software.log
Ignored by design: loaded_scripts.log is skipped completely. It reflects Zeek runtime configuration rather than network behavior, and it adds noise to summaries and plots without helping malicious-traffic detection.

Single-File Mode: What -f Does and Does Not Use

-f analyzes exactly one Zeek log. The columns printed in the anomaly table are kept to help the analyst understand each row; they are not necessarily model inputs.

What still happens

  • The file is loaded and its log type is inferred from the filename stem.
  • The matching feature builder and scorer run on all rows in that file.
  • Rows receive score and pred, and the top -a selected rows are printed.
  • Original Zeek columns remain visible so a human can investigate the result.

What is unavailable

  • No other Zeek logs are loaded, so there is no cross-log uid or fuid evidence.
  • No directory maliciousness score or source-level scan behavior score is produced.
  • No normal-directory baseline comparison is performed; -N is a directory-mode feature.
  • --summary-line is also a directory-mode feature.

Processing Pipeline

The tool follows a structured sequence so that log-specific scoring can still benefit from directory-wide context.

1

Discover logs

In directory mode, the tool enumerates .log files, skips ignored logs, and skips empty files cleanly rather than aborting the whole run.

2

Load data

Each file is loaded as a pandas DataFrame. TSV logs use Zeek headers when available. JSON logs are parsed as line-delimited records.

3

Build shared context

Before scoring any file, the tool constructs directory-wide context from all loaded logs. This creates per-uid aggregates and file metadata lookups used later by conn, http, files, dns, ssh, and other feature builders.

4

Engineer features per log type

Each log type gets a different feature builder. The builders generate numeric features, categorical rarity scores, cross-log counts, ratios, lexical measures, or time-series derivatives depending on what the schema means.

5

Apply a log-specific scorer

The tool picks a scorer per log family: PCA flow scoring, multivariate Isolation Forest, hybrid DNS logic, rarity scoring, time-series deviation scoring, or a fallback distance method when the feature space is too small.

6

Produce per-file anomaly rankings

Each file returns row-level scores, predicted anomalous rows, score percentiles, and metadata for printing, plotting, and JSON export.

7

Build a directory-level maliciousness score

The final score combines the strongest per-file anomaly concentration, cross-log overlap, weird/notice bonuses, HTTP-file overlap, and an explicit connection-behavior scan profile.

Feature Engineering

A feature is simply a number that represents one useful property of a log row. The detector turns text, lists, flags, and related records into numbers because the scoring methods operate on numeric tables. Open any log family below to see exactly what is computed and a small example.

Four naming rules make the tables easier to read. A *_count feature counts items; *_len counts characters; is_* and other Boolean features are 1 for yes and 0 for no; and *_rarity is -ln(frequency). For example, a value seen in 50 of 100 rows has rarity 0.69, while a value seen once has rarity 4.61. Missing numeric values such as Zeek's - are converted to zero.

Unknown log types: generic feature builder

For an unrecognized Zeek log, ts, uid, and fuid are excluded. Every remaining column that can be parsed numerically keeps its original name and becomes a numeric feature; every text column becomes <column>_rarity.

Example: numeric attempts=7 remains attempts=7; text action=blocked seen once among 100 rows becomes action_rarity=4.61.

Models and Scoring Techniques

A score answers one question: “How unusual is this row compared with the other rows in the same log?” It is not a probability of attack. Before scoring, every method removes columns that have only one value because a constant column cannot distinguish one row from another.

PCA: how conn.log anomalies are found

PCA means Principal Component Analysis. Imagine plotting every connection as a point. With only two features, the horizontal axis might be duration and the vertical axis might be response bytes. Real data has eight axes, but the idea is the same.

  1. Build the table. Each row is one connection and the columns are duration, originator bytes, responder port, responder bytes, originator IP bytes, responder packets, responder IP bytes, and IP protocol.
  2. Put features on comparable scales. PyOD standardizes every column to mean 0 and standard deviation 1. Without this step, a byte count in the millions would overwhelm a protocol number such as 6.
  3. Learn the normal directions. PCA finds new axes—called principal components—that summarize how features vary together. For example, response bytes and response packets normally increase together, so PCA learns that common direction.
  4. Measure departure from those patterns. PyOD measures each standardized row's distance to the learned component vectors. Contributions are divided by explained variance, so components with smaller explained variance have more influence on the score.
  5. Rank and label. Larger distance means a larger anomaly score. PyOD's default contamination is 0.10, so roughly the highest-scoring 10% receive pred=1. The -a option controls how many of those labeled rows are printed; it does not change PCA's 10% threshold.
Tiny example: suppose ordinary downloads have 100 response packets and about 100 KB, while large downloads have 1,000 packets and about 1 MB. Those two features grow together. A flow with 1,000 packets but only 2 KB breaks that learned relationship and can score highly. A flow with exceptionally large byte counts can also be far from the center and score highly even when its ratios look ordinary. PCA says “unusual combination,” not “malicious.”

Isolation Forest: isolate unusual transactions quickly

Used for http.log, files.log, ssh.log, and tls.log. It does not try to draw one boundary around normal traffic. Instead, it asks how quickly a row can be separated from all other rows.

  1. Choose a feature at random, such as response body length.
  2. Choose a random split value, such as 40,000 bytes.
  3. Repeat the random splits until rows are isolated in a tree.
  4. Build 200 such trees and average the result.

A common row buried inside a dense cluster needs many splits. A strange row far from the others is often isolated in only a few splits, so it gets a higher anomaly score. The implementation uses a fixed random seed for repeatability. Its expected anomaly fraction is amountanom / row_count, limited to the range 1%–20%.

Tiny example: among 1,000 HTTP rows, 990 are GET requests with small responses. One row has a rare method, a 200-character URI, a 500 MB response, and a linked executable. Random splits isolate that unusual combination quickly. With -a 10, contamination is 10/1000 = 1%.

Rarity scoring: add up uncommon evidence

Event and inventory logs often have no dense numeric geometry to learn. For them, an uncommon event name, host, service, MAC address, or state can be the useful signal. A categorical value's rarity is:

rarity(value) = -ln(rows_with_value / all_rows)

A value in every row scores 0. A value in 50 of 100 rows scores 0.69. A value in 1 of 100 rows scores 4.61. The scorer adds every varying feature in that builder and marks the top -a rows.

Tiny example: a weird event has name_rarity=4.61, source_rarity=2.30, and peer_rarity=0.69. Ignoring its other fields, its summed score is 7.60.

Exact implementation detail: all varying numeric builder outputs are summed, not only fields ending in _rarity. Raw values such as a port number, timestamp, message length, or Boolean flag can therefore also affect the scale. Scores are meaningful only within that file.

Hybrid DNS scoring: suspicious evidence minus benign discovery

DNS needs domain knowledge because random-looking names can be suspicious while mDNS, reverse lookups, and service discovery are often harmless. The scorer first converts each selected signal to an absolute z-score—how many standard deviations it is from that log's average—and applies explicit weights.

score = unusual DNS evidence + direct DGA bonuses - benign-discovery penalties score = max(0, score)
  • Strong positive evidence: dga_like, many DGA-like queries from the source, repeated DGA-shaped patterns, high entropy, diverse characters, digits, rare query/TLD/type/response, no answer, rejection, and related weird events.
  • Direct bonuses make an actual DGA flag and repeated DGA behavior matter even before comparison with the average row.
  • Penalties subtract 6 for mDNS, 6 for .local, 5 for reverse lookup, and 5 for service discovery. Negative totals are clipped to zero.
  • The top -a scores receive pred=1.
Tiny example: x7k2m9qz12.example has high entropy, many unique characters, digits, no answer, and six similar queries from the same source, so several positive terms reinforce one another. In contrast, _ipp._tcp.local on port 5353 activates mDNS, local-TLD, and service-discovery penalties and is pushed toward zero.

Only the signals named above enter the current DNS score directly. Other DNS features in the feature dictionary are computed for inspection and future model changes.

Time-series deviation: unusual level plus unusual change

Rows in stats.log and capture_loss.log are ordered measurements, so the previous row matters. For every varying feature, the scorer adds two quantities:

feature contribution = abs(z-score of current value) + abs(z-score of change from previous row)

The first term catches an unusually high or low level. The second catches a sudden jump or drop, even when the new level is not yet extreme. Contributions from all features are added, and the top -a rows receive pred=1.

Tiny example: the event queue normally stays between 8 and 12, then jumps from 10 to 500. The value 500 has a large level z-score, and the change +490 has a large change z-score, so that timestamp receives two strong contributions.

Fallback standardized distance

Isolation Forest is skipped when it is unavailable, when fewer than two varying features exist, or when fewer than eight rows exist. PCA also falls back when PyOD is unavailable or there are too few rows/features. The fallback standardizes each feature and adds absolute z-scores:

fallback_score(row) = sum(abs((value - mean) / standard_deviation))

This is simpler than PCA or Isolation Forest: it notices individually extreme values but is less able to learn complex relationships between features. The top -a rows are labeled.

How to interpret the output: score is a within-log ranking number; pred=1 means the method selected the row as an outlier. Neither means “confirmed attack,” and raw scores from different methods are not comparable. A PCA score of one million is not automatically more dangerous than a DNS score of 20. Directory aggregation uses within-file percentile ranks where cross-file comparison is needed.

Directory Maliciousness Score

The final directory score is not a raw sum of anomaly scores. It is a weighted summary of several normalized behaviors.

core_score = 100 * ( 0.35 * weighted_top + 0.25 * uid_corr_score + 0.20 * weighted_fraction + 0.15 * weird_notice_bonus + 0.05 * fuid_bonus ) directory_score = min(100, core_score + 45 * behavior_score)

What the components mean

  • weighted_top: how strong the top anomalies are inside each file, after weighting by log importance
  • weighted_fraction: how much anomaly mass is spread across each file, again weighted by log importance
  • uid_corr_score: how many anomalous uid values are shared across multiple log types
  • weird_notice_bonus: extra weight when already-exceptional logs contribute anomalous rows
  • fuid_bonus: extra weight when anomalous HTTP rows overlap with anomalous files through fuid
  • behavior_score: explicit source-level scan behavior from conn.log

Why the behavior score exists

Some attack directories, especially simple scans, do not generate much uid overlap into higher-level logs. A separate behavior stage over conn.log captures source fan-out, failed-connection fraction, short-connection fraction, zero-payload fraction, and maximum per-host port sweep. This is what allows the detector to recognize broad scan campaigns as strongly malicious even when the higher-level logs are sparse.

Normal Baseline Training

The baseline logic is designed for the reality that “normal” Zeek directories still vary a lot.

Why not train on raw anomaly scores?

Raw row-level scores vary across log types, detector families, traffic volumes, and capture duration. Training thresholds directly on those values would be unstable and hard to interpret.

What is actually trained

The tool learns thresholds from directory-summary metrics such as:

  • score
  • weighted_top
  • weighted_fraction
  • uid_corr_score
  • weird_notice_bonus
  • fuid_bonus
  • behavior_score
  • conn_scan_score
  • cross-log overlap counts

How thresholds are learned

  • With multiple normal directories, the tool uses robust statistics: median and MAD-based upper bounds
  • With very few normal directories, it falls back to conservative upper margins above observed normals
Interpretation: the baseline comparison is not asking “is this exact row anomalous?” It is asking whether the directory’s aggregate behavior exceeds what was observed in known-normal directories.

Outputs and Interfaces

Default terminal mode

Prints anomaly tables per file and, in directory mode, prints a final directory summary and optional baseline comparison.

--summary-line

Suppresses the normal terminal output and prints one final tab-separated line with input path, score, severity, and baseline verdict if present. In ANSI-capable terminals, the score and verdict fields are colorized.

JSON export

Exports per-file summaries, anomalous identifiers, top rows, directory summary, and optional baseline comparison.

PDF plot export

Exports a summary page, a combined flow-by-flow normalized score page, and one score plot per analyzed log file. When a baseline is present, the summary plot overlays suspect bars, normal medians, and normal thresholds.

Design Decisions and Why They Were Made

  • Per-log detectors instead of one model: because Zeek logs have incompatible semantics
  • Cross-log context before scoring: because many attacks are only obvious when logs are tied together
  • Explicit DNS and scan logic: because generic unsupervised scoring often misses DGAs and simple sweeps
  • Directory-level scoring from normalized components: because raw anomaly scores do not compare cleanly across logs
  • Robust baseline training: because normal traffic varies and naive fixed thresholds are brittle
  • Ignore loaded_scripts.log: because runtime configuration noise was hurting detection quality more than helping
What the tool does not claim: the final directory score is not a calibrated probability of compromise. It is a triage-oriented maliciousness score meant to help rank directories and focus analyst attention.

How to Use

Single file

python3 zeek_anomaly_detector.py -f conn.log

In this mode only conn.log is analyzed. PCA uses its eight documented numeric inputs; the remaining printed columns are explanatory context. Use directory mode when you want cross-log correlation, scan behavior scoring, a directory score, or baseline comparison.

Directory analysis

python3 zeek_anomaly_detector.py -d /path/to/zeek

With normal baseline

python3 zeek_anomaly_detector.py \
  -d /path/to/suspect \
  -N /path/to/normal1 \
  -N /path/to/normal2

One-line final summary

python3 zeek_anomaly_detector.py \
  -d /path/to/suspect \
  -N /path/to/normal1 \
  --summary-line

Export JSON and plots

python3 zeek_anomaly_detector.py \
  -d /path/to/zeek \
  -J summary.json \
  -P scores.pdf
